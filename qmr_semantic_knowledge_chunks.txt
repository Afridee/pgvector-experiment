---
title: Date range is split between monthly materialized caches and live daily cache when “current date” is included
tags: dates, materialized-view, monthly_order_cache, daily_order_cache, split-range
content:
The report checks whether today’s date (system currentDate) falls inside the requested [startDate, endDate] (inclusive).
- If today is inside the range, the query is split:
  - Historical portion uses monthly materialized-cache tables up to “yesterday” (mv_end_date = currentDate - 1 day).
  - Live portion uses the daily cache table for [currentDate, endDate + 1 day).
- If today is not inside the range, the entire query uses only the monthly materialized-cache tables up to endDate.
---

---
title: Monthly cache table naming and selection logic
tags: monthly tables, table suffix, partitioning, monthly_order_cache
content:
Monthly data is read from tables named:
- monthly_order_cache_<YYYY>_<MM> (e.g., monthly_order_cache_2026_02)

The code generates the list of monthly table names by iterating month-by-month starting at the first day of startDate’s month through mv_end_date’s month (inclusive). These tables are later UNION ALL’d together.

---
title: Inclusive end date implemented via “endDatePlusOne” half-open interval
tags: dates, endDatePlusOne, time window, half-open interval
content:
Date filters use half-open ranges:
- order_placed_at >= startDate
- order_placed_at < endBoundary

Where:
- endDatePlusOne = endDate + 1 day, so [startDate, endDatePlusOne) includes the full endDate day.
For monthly materialized queries, the end boundary is mvEndDateStr:
- If the query is split (today included): mvEndDateStr = currentDate (so monthly caches cover [startDate, currentDate))
- Otherwise: mvEndDateStr = endDatePlusOne (so monthly caches cover [startDate, endDate+1))
For daily cache queries (only when split): [currentDate, endDatePlusOne).

title: Primary sales data source tables and pattern (monthly vs daily)
tags: SQL pattern, primaryDataQuery, monthly_order_cache, daily_order_cache, union-all
content:
Primary KPI data comes from:
- monthly_order_cache_YYYY_MM tables (multiple, UNION ALL)
- plus daily_order_cache (only if today is within the date range)

All per-table queries share the same SELECT fields, WHERE filters, and GROUP BY keys, then are combined with UNION ALL and re-aggregated in an outer query (SUM of Memo and STT) to consolidate duplicates across partitions.

productType is read from query.productType (default “SKU”), lowercased, then mapped to canonical capitalization:

- "family" → "Family"

This canonical value drives:

- how product filters are applied
- which Excel generator function is called
- whether productQuery and retailerOrderData are meaningful or replaced with a dummy query

title: Key KPIs: “Memo” distinct-count definition and “STT” sum definition
tags: KPI, Memo, STT, distinct-count, aggregation
content:
Two main KPIs are computed from the order cache tables:

1) Memo:
- Defined as COUNT(DISTINCT retailer_id + '-' + DATE(order_placed_at) [+ '-' + product_id]).
- For non-Total product types: distinct key includes product id, so Memo is per (retailer, day, product).
- For Total product type: distinct key excludes product id, so Memo is per (retailer, day) overall.

2) STT:
- Defined as SUM(o.total_stt).

These are computed per partition-table query, then summed again in an outer aggregation after UNION ALL.

title: Cross-partition consolidation: outer query sums per-group Memo and STT
tags: union-all, outer group by, re-aggregation
content:
Because data is pulled from multiple monthly tables (and possibly daily cache) via UNION ALL, the final step wraps the UNION ALL in an outer SELECT that:
- GROUP BY the same dimensional fields (including product id where applicable)
- Computes SUM("Memo") and SUM("STT")

This ensures the final dataset is consolidated across all partitions.

title: “Retailer order” query provides Total Memo per retailer-day independent of product
tags: retailerOrderData, Total Memo, distinct-count
content:
A second dataset is computed (only when productType != Total) to represent retailer-level activity:

- Total Memo = COUNT(DISTINCT retailer_id + '-' + DATE(order_placed_at))
- Grouped by: retailer_code, RouteSectionId, pointId

This query is also run per monthly table (and daily cache if split), UNION ALL’d, then summed in an outer query:
- SUM("Total Memo") grouped by retailer_code, RouteSectionId, pointId

This metric is intentionally NOT split by product, even when the main report is by SKU/Brand/Family/Segment.

title: Filter list parsing: “all” values are removed (or nullified) before SQL IN clauses
tags: filters, all, IN clause, region, area, territory, distributor, point
content:
Several filters are turned into comma-separated lists for SQL IN (...) clauses. For region/area/distributor/territory/point:
- If the filter list contains items equal to the string "all", those are excluded.
- If, after excluding "all", the list is empty, the filter condition is omitted entirely.
Affected filters:
- regionFilter → o.region_id IN (...)
- areaFilter → o.area_id IN (...)
- distributorFilter (house) → o.house_id IN (...)
- territoryFilter → o.territory_id IN (...)
- pointFilter → o.point_id IN (...)
---

---
title: SubChannel filter behavior differs: “all” is NOT removed
tags: subChannelFilter, filters, potential behavior
content:
subChannelFilter is built from query.subChannelFilter without removing "all".
As a result, if "all" appears in subChannelFilter, it will be included in:
- o.sub_channel_id IN (subChannelFilter)
This differs from region/area/distributor/territory/point filters which explicitly remove "all".

title: Product filter application depends on product type; Total uses SKU filter path
tags: productFilter, SKU, Brand, Family, Segment, Total, IN clause
content:
products is a comma-separated list from query.productFilter (no special “all” removal shown).

In the primary/daily cache WHERE clause, the product filter is applied as follows:
- If productType in ("SKU", "Total"): filter by o.sku_id IN (products)
- If productType == "Brand": filter by o.brand_id IN (products)
- If productType == "Family": filter by o.family_id IN (products)
- If productType == "Segment": filter by o.segment_id IN (products)

Notably, “Total” still applies productFilter to o.sku_id (if products is provided).

title: Active status filter normalization and meaning
tags: activeStatus, current, inactive, all, boolean mapping
content:
activeStatus is read from query.activeStatus and normalized:
- If activeStatus is a list with:
  - "all" present OR length > 1 → activeStatus becomes None (no active filtering)
  - Exactly one value:
    - "current" → activeStatus = "true"
    - otherwise → activeStatus = "false"
- Any other shape or empty → activeStatus = None

This activeStatus is used only in productQuery (dimension tables), not in the cache-table primary queries.

title: Product dimension query (productQuery) joins SKU to Brand/Family/Segment and uses show_in_report
tags: productQuery, fmc_products, brands, families, segments, show_in_report, sort_priority
content:
For non-Total product types, product metadata is retrieved from:
- fmc_products fp
  JOIN brands bnd ON fp.brand_id = bnd.id
  JOIN families fml ON fp.family_id = fml.id
  JOIN segments sg ON fp.segment_id = sg.id

Base rule:
- Only products with fp.show_in_report = true are included.
Ordering:
- ORDER BY fp.sort_priority ("Sort")

Returned fields include:
- fp.id as productId, fp.sku as SKU_Name, fp.sort_priority as Sort
- brandId + Brand_Name
- familyId + Family_Name
- segmentId + Segment_Name

title: Active status is applied selectively depending on report’s product type
tags: active filtering, brands.is_active, families.is_active, segments.is_active, fmc_products.is_active
content:
If activeStatus is set (true/false), it is applied differently based on productType:
- For Brand reports: adds condition on brands table: bnd.is_active = activeStatus
- For Family reports: adds condition on families table: fml.is_active = activeStatus
- For Segment reports: adds condition on segments table: sg.is_active = activeStatus
- For SKU reports: adds condition on fmc_products table: fp.is_active = activeStatus

This means “active” filtering is applied at the level of the grouped dimension, not uniformly across all joined tables.

title: Report type controls whether Memo and STT columns are shown
tags: reportType, showMemoColumn, showSttColumn, output columns
content:
reportType is read from query.reportType:
- If missing or equals ["all"] → treated as None (show everything)

Then:
- showSttColumn = ("stt" in reportType) if reportType else True
- showMemoColumn = ("memo" in reportType) if reportType else True

So by default both Memo and STT are included. If reportType is specified, only explicitly included metrics are shown.

content:
Both monthly cache queries and the daily cache query apply the same filter pattern:

---
title: Grain differences between primary data vs retailer-order data
tags: grain, grouping, primary vs retailer memo
content:
Primary data grain includes:
- point + retailer_code + retailer_name + routeSection + subchannel + cluster + tpg
- plus product id (except Total)

Retailer-order data grain includes:
- point + retailer_code + routeSection
(no retailer_name, no subchannel/cluster/tpg, and no product id)

This implies retailer-order is intended as a higher-level denominator/coverage metric compared to product-level primary metrics.
